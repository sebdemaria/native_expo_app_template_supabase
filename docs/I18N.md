# Localization Template

NutriPlan uses i18next + react-i18next with typed resources, Spanish and English. Expo Localization supplies device language tags; Zustand persists only the user's language preference.

## Behavior

- `system` (default for new installs): first supported device language, falling back to Spanish.
- `es` / `en`: explicit persisted override, independent of device language.
- Existing stored Spanish/English choices are preserved; invalid saved locales resolve to automatic mode.
- `LocalizationProvider` updates React when the preference changes or the device locale list changes. Resource loading is synchronous and local; no translation network request is needed.
- Missing English translations fall back to Spanish. Missing keys in both catalogs are development defects; completeness tests and TypeScript catch them.
- React escapes text; interpolation uses `escapeValue: false`, suitable for React Native. Never use translated untrusted input as raw HTML.

## UI Usage

```tsx
import { useTranslation } from "react-i18next";

const { t, i18n } = useTranslation("home");
// t("title") — typed namespace/key
// i18n.resolvedLanguage — effective language
```

Use `usePreferencesStore.getState().setLocale("es" | "en" | "system")` for selection. The scaffold includes `LanguageSelector` so the behavior can be tested before the Settings feature exists.

## Resources And Types

- `src/i18n/locales/es.ts`: source key shape, organized by namespace.
- `src/i18n/locales/en.ts`: the same structure enforced with `satisfies`.
- `src/i18n/types.d.ts`: typed keys/namespaces for i18next.
- `src/i18n/locale.ts`: pure normalization and fallback policy.
- `src/i18n/instance.ts`: independent translator factory.
- `src/i18n/provider.tsx`: reactive store/device integration.

Add user-facing copy to both catalogs, not inline in screens. Add new namespaces to both resources and the factory namespace list. Interpolation uses `{{variable}}`; pluralization uses i18next's `_one`/`_other` keys and a numeric `count`. Tests check key and interpolation parity, pluralization, fallback, device tags, reactive selection, and persisted preference restoration.

## Notifications And Backend

For background/local notification copy, create an independent `createAppI18n(locale)` instance. Never change the foreground instance's language from a background task. Include locale in notification reconciliation fingerprints so changed language updates scheduled copy.

Language is not timezone: date/week/reminder calculations still require an explicit IANA zone. Use locale-aware `Intl` formatters when those utilities are implemented. Server push/AI localization must receive an explicit user locale; backend translation integration is not implemented by this UI template.

## TetApp Adaptation

Reuses TetApp's concepts (supported languages, regional normalization, fallback, interpolation, completeness tests), not its mutable global locale or monolithic dictionary. Native branding/product-specific strings were not copied.

Theme preference is separate; this change does not implement the future theme selector or bilingual native permission descriptions/store metadata.
